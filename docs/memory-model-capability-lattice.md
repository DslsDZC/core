# 内存模型方向讨论备忘：能力模型 + 格（Capability + Lattice）

日期：2026-08-16
状态：**讨论中**——待广泛商议，未定稿。本备忘供参与者审阅。

## 一、背景：抽象升华系列

Core 的类型/内存设计遵循「抽象升华」原则（与 dex/apx 数值类型设计同系列）：

1. **核心语义 = 数学/逻辑/结构，零硬件惯例**——惯例只允许以「后端实现选择」或「可忽略注解」存在
2. **范式普适**：语言要跨越所有范式（量子、分布式、GPU、未来未知范式）
3. **用户面上手成本极低**：内部可以复杂（编译器承担），表面必须简单

## 二、位置抽象的两难

```
太复杂（全一般理论，如完备格代数全套）
  → 上手成本爆炸——用户要学格运算

太低端（纯 1D 扁平地址）
  → 范式特例跨不过——量子寄存器（纠缠是位置间关系，不是顺序）、
    分布式（node 是身份不是偏移）、GPU（bank 冲突）
```

## 三、结构性论证：位置识别的两种必然形式

「存东西」要求位置**可识别**。「指认位置」只有两种结构：

```
有序的位置 → 偏移原语（±4、连续坐标）
命名的位置 → 标签原语（内容寻址=hash、图节点、属性标识、句柄）
```

- 覆盖论证是结构性的（分析「指认位置」的必然），不是枚举范式
- 纯值流范式（函数式/数据流）**无位置概念**——值语义直接承载，位置抽象自动失效
- 边界声明：若出现「存了但无法指认」的存储——矛盾，不构成范式

## 四、候选品谱系（第一原语对比）

| 候选 | 第一原语 | 包含(区域) | 组合(分割) | 顺序(偏移) | 备注 |
|---|---|---|---|---|---|
| **格（Lattice）** | 偏序 + join/meet | 支持 | 支持 | 支持（链是特例） | 一网打尽，公理重；区域嵌套已是它的影子 |
| **PCM（偏交换幺半群）** | 分割/组合 `·` | 支持（序从组合导出） | 支持，最精确 | 不支持，需外加链结构 | 分离逻辑真实底座（Iris ghost state）；比格弱、更准 |
| **树/层级** | 唯一父结构 | 支持（严格层级） | 不支持，无合并 | 支持（层内序） | 简单，但「两个区域并成一个」表达不了 |
| **向量空间** | N-D 坐标 | 不支持 | 不支持 | 支持，最自然 | 纯偏移；区域/组合语义缺席 |
| **能力模型（Capability）** | 句柄 + 权限 | 支持（能力含区域） | 支持（能力可分割） | 不支持（能力不可算术） | CHERI/seL4 先例；安全性最强 |

## 五、方向：能力模型 + 格（互补闭环）

```
能力解决「怎么指」：位置 = 句柄 + 权限 + 边界（不可裸算）
格解决「怎么组织」：能力的代数——包含（域嵌套）/ 组合（分割合并）/ 细化（降权）

缺口互补：
  能力缺的偏移   → 能力内相对游标（base + offset，边界由能力携带——bounds by construction）
  格缺的安全     → 能力自带权限与边界
  格缺的顺序     → 偏移作为能力的内部视图存在（不能脱离能力）
```

### 形态

```
用户面：能力（不透明句柄）+ 能力内相对偏移——零裸地址，权限显式
内部：  能力的格——⊑ 细化（读写能力 ⊑ 只读能力）、join 组合、meet 交集
        区域格（嵌套区域 = 能力的域）+ 权限格（读/写/执行 + 扩展权限）
```

## 六、与现有机器件的映射（升级不是推翻）

| 现有 | 升级为 |
|---|---|
| PointerAnalysis（pts） | 能力流分析（能力如何派生/传递） |
| RegionCheck（区域逃逸） | 能力的包含格（域嵌套 = 格序） |

| IR_BOUNDS_CHECK（已有） | 运行期能力边界检查（能力模型的软实现） |

## 七、诚实的代价

- **性能**：能力检查有成本——CHERI 用硬件摊；软件路线 = 编译期格推理（免费）+ 运行期边界检查（Core 已有基建）
- **工程量**：三 pass 重写 + 类型系统携带权限位——内存模型层面的大改
- **验证层影响**：能力/权限语义进规约（能力作为验证对象）

## 八、开放问题（供商议）

1. 权限位集：读/写/执行 + 哪些扩展权限？（引用传递？派生限制？）
2. 能力的派生规则：谁能降权/组合？派生链如何追踪（能力流分析的范围）？
3. 偏移的边界语义：能力内相对偏移的越界 = 不可表达（类型层）还是检查（运行期）？
4. 验证层：能力/权限如何进规约（能力作为验证对象）？
5. 性能路线：纯软件（编译期格推理 + 运行期检查）vs 未来硬件化（CHERI 式）？
6. 与 arena 模型的关系：区域 = 能力的域——arena init/new/reset 如何映射到能力生命周期？
7. 用户面语法：能力如何书写（句柄类型？权限标注？）——上手成本约束下最小语法是什么？
