# Core 惰性求值

## 设计原则

- **图本来就是惰性的。** 节点不在边上游等待时就不执行。当前的 IR 生成策略是 eager——节点一出现就执行。这不是图的限制，是策略的选择。

## 自动惰性推导

编译器看图决定一个节点是否需要惰性求值：

```core
result := if cond {
    expensive1()     // 只在 cond=true 时用到
} else {
    0                // cond=false 时到这里
}
print(result);
```

| 条件 | 策略 |
|------|------|
| 节点结果只用在一个分支里 | 延迟到确定需要时执行 |
| 节点有副作用（IO、文件、volatile） | 永远 eager，不惰性 |
| 节点在循环体内且每次都用 | eager |
| 节点在循环体内但条件性用 | 惰性 |

## 无关键字

惰性推导和之前的指针验证、编译期求值、概率推导一样——编译器看图自动做，不引入 `lazy` 关键字。

```core
x := expensive();       // 编译器 auto: eager 或 lazy
y := cond ? x : 0;      // 如果 x 只用在这里且无副作用 → 自动惰性
```

## 副作用标记

编译器需要知道哪些节点有副作用。纯函数的调用自动可惰性。副作用的标记来源：

| 来源 | 判定 |
|------|------|
| 纯函数（无 IO、无变异） | 可惰性 |
| IO 操作（read_file、print） | 不可惰性 |
| volatile 内存操作 | 不可惰性 |
| FFI 调用 | 默认不可惰性 |

## 被推导但是用了怎么办

```core
x := expensive();   // 编译器决定惰性
y := cond ? x : 0;
z := x + 1;         // x 这里也被用了 → 必须求值
```

如果编译器发现惰性标注的节点实际上有多条路径需要它——自动升级为 eager。用户不感知。

## 惰性不改变语义

无论编译器选择惰性还是 eager，程序输出一致。惰性只是策略选择，不影响正确性。
